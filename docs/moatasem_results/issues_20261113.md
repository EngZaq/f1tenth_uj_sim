# Mission issues found on 13 November 2026 (simulation)

Found while running `tools/mission/full_autonomy.py --autonomous --start-simulator --mapping-only`.
The run folders are under `results/missions/`. No team file was changed. These are proposals only.

---

## (a) A second Ctrl+C during cleanup leaves the whole stack running

**What happened.** In run `autonomous_20261113_194051_328845` the operator pressed Ctrl+C during
EXPLORING. After the mission had exited, these processes were still running: the drive watchdog,
`sim_vesc_imu`, `fusion_scan_relay`, `mission_first_lap`, `mission_explore`, and `map_server`,
`lifecycle_manager` and `ego_robot_state_publisher` from the simulator launch. The EKF, SLAM and
gym_bridge had to be killed by hand. The explorer kept logging for more than 10 minutes after the
mission ended. Any later run then shares domain 43 with these nodes.

**Cause** (`full_autonomy.py`):
1. Every child starts with `start_new_session=True` (line 57). That is correct for `killpg`, but it
   also means a child never receives the terminal's SIGINT or SIGHUP. Only `close()` can stop it.
2. `close()` (lines 104-120) first runs two `ros2 topic pub --once` commands and only then stops
   any child. In Humble, `--once` waits for one matching subscriber, and during mapping nothing
   subscribes to `/amcl_drive/enable`. So that command always runs until its 3 s timeout. With one
   Ctrl+C, cleanup took 16 s in total (test run `..._201924_746763`).
3. A second Ctrl+C during that time raises `KeyboardInterrupt`. That is a `BaseException`, so
   `except Exception` (lines 110 and 114) does not catch it. `close()` stops before its first
   `stop()`, the script exits, and every child is orphaned. In run 194051 the zip was written
   5 s after STOPPED, and no command from `close()` was logged.
4. The same thing happens on SIGTERM or SIGHUP to the mission, for example when the terminal or
   VS Code is closed. Python's default handlers for those signals exit without running `finally`.

**Evidence that the normal paths work.** A normal finish (run `..._201427_961553`) and a single
Ctrl+C (run `..._201924_746763`) both left no process behind.

**Proposed minimal fix:**
```python
# Mission.close(), right after `if not self.jobs: return`
signal.signal(signal.SIGINT, signal.SIG_IGN)   # a repeated Ctrl+C must not abort cleanup

# main(), before `try: run_mission(ctx, args)`
def _interrupt(signum, frame):
    raise KeyboardInterrupt
signal.signal(signal.SIGTERM, _interrupt)
signal.signal(signal.SIGHUP, _interrupt)
```
The `ros2` commands inside `close()` already have timeouts, so ignoring SIGINT cannot hang it.
Optional: skip the `/amcl_drive/enable` publish when no AMCL stage ran, or pass `-w 0`. That removes
3 s of dead time from every stop.

## (b) The lap check uses EKF odometry and passes or fails by millimetres

`mission_first_lap.py` ends exploration when **EKF odometry** (`/odometry/filtered`, frame
`fusion_odom`) comes back within `return_distance_m = 0.85` m and 48° of the start. It also checks
that the map corridor is closed. `slam_map -> fusion_base` is read only *after* that, to record the
final pose.

| Run | Result | Odom return distance |
|---|---|---|
| `autonomous_20261113_193348_154146` | lap detected | **0.846 m** (4 mm inside) |
| `autonomous_20261113_201427_961553` | lap detected | **0.847 m** (3 mm inside) |
| `autonomous_20261113_194051_328845` | never ended (stopped after 11 min) | closest logged: **0.99 m** at 34.4 m, 1.22 m at 69.8 m |

The lap is about 34 m. EKF dead-reckoning drift at the closing point is already about 0.85 m and it
keeps growing on later passes. So the check only works when the drift happens to fall just under the
threshold.

**Proposal.** Use the **`slam_map -> fusion_base`** pose for the return test: record its value as the
start once SLAM publishes, then compare against it. SLAM corrects the drift with scan matching. It
does that even with loop closing off, because the car is matching against map cells it built at the
start. The odometry distance can stay as the travelled-distance gate (`min_distance_m`).

**About 0.85 m.**
- If the check switches to the SLAM pose: keep 0.85 m. It is a reasonable "same place" tolerance for
  a pose that does not drift.
- If the check stays on EKF odometry: 0.85 m is too tight. It would need about 1.2-1.5 m, and that
  risks ending the lap early on tracks where two sections pass close to each other. The heading
  check (48°) and the corridor-closed check reduce that risk, but they do not remove it.

We recommend switching to the SLAM pose rather than raising the threshold.

## (c) Preflight does not detect leaked simulator nodes

Preflight (`full_autonomy.py` line 181) refuses to start only when one of `LOCALIZATION_CONFLICTS`
(`tools/mission/ros_graph.py`) or `/simulation_drive_watchdog` is running. It does not check for
simulator nodes. In run 194051, `/map_server`, `/lifecycle_manager_localization` and
`/ego_robot_state_publisher` stayed alive after their launch process had died. The next
`--start-simulator` run would start a second copy of each one, and preflight would not report it.
That gives duplicate node names, a second `/map` publisher, and duplicate URDF `/tf_static` entries.
A leaked `/bridge` makes it worse: `/ego_racecar/odom` then has 2 publishers, so the
`Publisher count: 1` readiness test never passes, and a leaked `foxglove_bridge` keeps port 8765.

**Proposal.** When `--start-simulator` is given, also refuse to start if any of these are present:
`/bridge`, `/ego_robot_state_publisher`, `/map_server`, `/lifecycle_manager_localization`,
`/foxglove_bridge`. Also check that `/scan` and `/ego_racecar/odom` have 0 publishers. The error
message should list the node names that were found.
